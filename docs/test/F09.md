# Kiểm thử F09 — Workflow và tự động snapshot CDE khi publish Data Dictionary

## Điều kiện chuẩn bị

| Đối tượng | Điều kiện |
| --- | --- |
| Data Proposer | Có `canViewWorking`, `canEditWorking`, `canSubmit`; không có `canApprove` |
| Data Steward/Reviewer | Có `canViewWorking`, `canApprove`, `canReject`; không có `canEditWorking` |
| Consumer-only | Có `canViewPublished`, không có `canViewWorking` |
| Data Dictionary | Có working version `Draft`, `workingRevision >= 1`, `termRevisions = []` |
| CDE A | Latest active Approved `1.0` |
| CDE B | Approved `1.0` và working `1.1 Draft` |
| CDE C | Chỉ có working `Draft`, chưa từng Approved |
| CDE D | Latest Approved đã archive và không còn active published head |
| CDE E | Active Approved nhưng thuộc Glossary/Data Dictionary khác |
| Công cụ | DevTools/Network; quyền truy vấn database test để đối chiếu snapshot, relation, head và outbox |

## Contract bắt buộc

Các endpoint Submit, Reject, Reopen và Approve chỉ nhận:

```json
{
  "expectedRevision": 2
}
```

Request có `businessVersion`, `payload`, `termRevisions`, actor, timestamp, source/target status hoặc field khác phải nhận `400` và không thay đổi working/snapshot/head/outbox.

## Kịch bản kiểm thử cốt lõi

| Mã | Kịch bản | Các bước thực hiện | Kết quả mong đợi |
| --- | --- | --- | --- |
| F09-01 | Submit không đóng băng CDE | Submit Data Dictionary Draft rồi đọc working payload. | Chuyển sang `InReview`, revision tăng một; `termRevisions` vẫn rỗng; không tạo snapshot/head/outbox/relation. |
| F09-02 | Reject và Reopen | Reject bản InReview, sau đó Reopen bằng revision mới nhất. | `InReview → Rejected → Draft`; mỗi transition tăng revision một; không thay đổi business payload hoặc tạo publication data. |
| F09-03 | Preview động | Gọi `GET /working/publish-preview?limit=10`, duyệt cursor, sau đó approve thêm một CDE và gọi lại. | DTO có `data`, `paging`, `termCount`, `evaluatedAt`; không trả quá limit; preview thứ hai phản ánh active Approved head hiện tại và ghi rõ không ràng buộc lần Approve. |
| F09-04 | Tự chọn latest Approved | Approve Data Dictionary khi A=Approved 1.0, B=Approved 1.0 + Draft 1.1, C chưa Approved. | Snapshot chứa A 1.0 và B 1.0; không chứa B 1.1 hoặc C; không có thao tác chọn thủ công. |
| F09-05 | Trạng thái hiện tại tại Approve | Lấy preview, sau đó approve CDE C trước khi bấm Approve Data Dictionary. | Snapshot cuối cùng có CDE C vì C đã commit Approved trước khi transaction Data Dictionary lấy publication lock; response backend là nguồn có thẩm quyền. |
| F09-06 | Mutation CDE sau publication lock | Giữ transaction Approve Data Dictionary sau khi lấy parent lock, đồng thời gửi Approve CDE khác. | Approve CDE phải chờ; Data Dictionary snapshot không chứa version vừa chờ; CDE chỉ tham gia lần publish Data Dictionary tiếp theo. |
| F09-07 | Lọc sai phạm vi và inactive | Publish với CDE D archived, CDE E thuộc Glossary khác và fixture soft-deleted. | Không CDE nào trong ba trường hợp được đưa vào; không lộ payload qua preview hoặc published API. |
| F09-08 | Snapshot rỗng | Không có CDE nào có active Approved head rồi Approve Data Dictionary. | Publish thành công với `termRevisions=[]`, `termCount=0`; Consumer mở được Data Dictionary và thấy empty state. |
| F09-09 | Thứ tự xác định | Tạo CDE có name khác hoa/thường và trùng name, publish trên MySQL/PostgreSQL. | Thứ tự theo `name.toLowerCase(Locale.ROOT) → raw name → termId`; `displayOrder` liên tục từ 0 và giống nhau trên hai database. |
| F09-10 | Payload/relation/hash đồng nhất | Publish nhiều CDE rồi đọc snapshot JSON, `glossary_snapshot_term`, outbox và recompute hash. | Reference một-một, cùng thứ tự; hash khớp canonical payload và bao phủ `termRevisions`; outbox mang chính payload đã lưu. |
| F09-11 | Rollback từng boundary | Inject lỗi sau dựng refs, insert snapshot, insert relation, update head, insert outbox và delete working. | Mỗi lỗi rollback toàn bộ; không có snapshot/head/relation/outbox mồ côi; working InReview còn nguyên revision. |
| F09-12 | Concurrent Approve/Reject | Gửi Approve và Reject cùng `expectedRevision`. | Chỉ một mutation thành công; request còn lại nhận `409/404`; không đồng thời tồn tại snapshot Approved và working Rejected. |
| F09-13 | Snapshot cũ bất biến | Sau khi publish Data Dictionary v1.0, approve/archive CDE hoặc publish version CDE mới. | `termRevisions`, hash và kết quả đọc v1.0 không đổi; thay đổi chỉ xuất hiện trong Data Dictionary version publish tiếp theo. |
| F09-14 | Loại contract F08 cũ | Kiểm tra UI/API khi working/InReview/Approved. | Không có add/remove/pin; `/working/terms` và wrapper cũ đã bị xóa; UI không hiển thị “selected for release package” và dùng publish-preview mới. |
| F09-15 | Authorization | Thử từng transition/preview bằng Proposer, Steward/Reviewer, Consumer-only và user nhiều role. | Backend quyết định theo capability hiệu lực; Consumer không nhận working/preview; UI không render action trước khi có permission. |
| F09-16 | Validation request | Gửi thiếu/sai `expectedRevision`, revision cũ, field ngoài allowlist và sai source state. | Lần lượt nhận `400` hoặc `409` đúng contract; không thay đổi dữ liệu. |
| F09-17 | Tải lớn | Publish Data Dictionary có 10.000 active Approved CDE trên MySQL và PostgreSQL. | Không N+1, không truncate, đủ 10.000 refs/relation, thứ tự ổn định; payload/outbox nằm trong giới hạn vận hành đã cấu hình. |
| F09-18 | UI sau Approve | Mở modal, double-click Approve và quan sát response/navigation. | Modal tải preview mới nhất, action loading/disable, chỉ một request; UI dùng response để hiển thị `termCount`, chuyển read-only và tải terms từ published snapshot. |

## Failure boundary transaction

Thứ tự cần quan sát bằng test/instrumentation:

```text
lock Data Dictionary identity
→ lock/read working
→ authorize/validate
→ batch-read active CDE heads
→ build termRevisions + termCount
→ canonicalize + hash
→ insert snapshot
→ insert glossary_snapshot_term
→ update published head
→ insert outbox
→ delete working by expectedRevision
→ commit
```
